# Tasks

A Task is a **one-time scheduled agent run**: choose an agent, prompt, model, and time. At the chosen time the scheduler creates one Run. The Task stays on the Tasks page with its event log and a link to the Run. The Run page links back. For repeating work, use [Jobs](jobs.md) in Schedules; for tracked work that may need several steps, use Tickets.

Create a Task in **Agents → Tasks**. The form shows local time, its timezone, the model, and the latest acceptable start. The server stores an absolute UTC instant. A Task normally starts only if the scheduler reaches it within 60 minutes of its due time; this grace can be set from 1 minute to 24 hours. If the window is missed, the Task expires without a Run. The deadline concerns *admission* to the run queue; a concurrency wait after admission does not expire it. Tasks do not reserve quota or promise a successful model response.

The `tasks` platform Tool lets an agent schedule, list, inspect, reschedule, and cancel Tasks. New personas and workers receive the Tool by default, and can schedule **themselves**. Scheduling another agent needs either the existing **Can invoke other agents** grant or an explicit creator → target permission under Tasks. The target also has an **Accept scheduled Tasks** switch in its agent configuration. The platform checks authority when the Task is created, when it fires, and before its Run starts. Code-owned system agents cannot be scheduled through the ordinary Tool.

The model can be omitted in the Tool: the target's default is resolved and stored when the Task is created. An agent may select only the target's primary model or same-runtime backup model; an admin can select any model listed for the target runtime. Changing the target's runtime later blocks an incompatible Task rather than passing its old model to the wrong harness. A failed model Run remains linked to the Task and can be inspected in Runs and DLQ; it is not silently launched again.

A Task created from an external chat **does not automatically answer in that chat**. The creating persona should say where the result will appear; the Task log and Run are always available in the platform. A persona may separately use its owned chat connector to send a result. An internal Relay Task can reply in its source room only when the author and target still have access. Workers should use Jobs for recurring loops rather than indefinitely scheduling follow-ups.

The Tasks page has Upcoming, Past, and Needs attention views. Needs attention contains Tasks that expired, were blocked before starting, or linked to a failed Run. The Task log records creation, edits, claims, cancellation, blocking, expiry, and the Run handoff. Reporting counts Task-triggered Runs separately from Tasks that never launched. A cancelled Task is retained for audit; there is no delete action.
