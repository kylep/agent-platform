# 37 — One-time Tasks

Status: **implemented**, 2026-09-30. This document records the reviewed design; the implementation notes below distinguish shipped behavior from ideas retained for a later iteration. Tasks are a one-time counterpart to recurring Jobs: at a chosen instant, run a named agent with a stored prompt and model. The task remains visible after it fires, with its own event log and a link to the resulting Run. Agents may schedule themselves, workers, or other personas through a scoped platform Tool.

The shipped event log is stored in Postgres and the UI refreshes it by polling; a separate `tasks.events` Kafka topic is deferred. Model selection for agents is the target's primary or same-runtime backup; a separate `schedulable_models` list is deferred. The list API filters by status, target, and creator; project and due-window filters are deferred. Task records inherit team, project, and ticket context from their creator Run. Code-owned system agents are not Task targets. External-chat delivery is Task-log-only in this version and the Tool response states that explicitly. The remaining sections preserve the broader reviewed design and verification goals.

## User contract

“Ask Kai to check the weather tomorrow at 07:00” creates one Task. The UI immediately shows who requested it, who will run it, the exact time and zone, the model, the prompt, and where the result will appear. If a persona schedules from an external chat, its acknowledgement must name the delivery destination and link or identify the Task; the platform must not imply it will reply in Discord when it will only log the result. At the due time the platform launches one Run, records what happened, and never repeats the Task. A persona can create the same Task from Relay; the author is derived from its run identity. A worker can schedule a follow-up for itself or another agent. A human can create and edit a Task in the UI.

Tasks are **not Tickets** (tracked work that may need multiple actions) or **Jobs** (recurring cron). Their page title and Help copy always say “one-time scheduled agent runs.” A Task may link to a Ticket, project, team, or originating Relay conversation, but it does not replace any of those records.

## Data and execution

Add `scheduled_tasks` to Postgres. Fields: id, title, target_agent, prompt, requested_runtime, requested_model, run_at_utc, display_timezone, creator_participant, creator_agent, creator_run_id, root_run_id, inherited_depth, initiated_by, last_editor, source_conversation_id, source_message_id, delivery, ticket_id, project_id, team_id, status, run_id, last_observed_run_state, claim_owner, claim_generation, claim_until, last_deferral_reason, created_at, updated_at, fired_at, expires_at, version. Store the exact prompt, runtime, and selected model as a snapshot; never silently rewrite them after a target agent's configuration changes. `run_id` is deterministic for the Task and unique in both Task and Run records. A separate append-only `scheduled_task_events` table records created, edited, cancelled, claimed, run_queued, run_state_changed, expired, and launch_error with actor, timestamp, reason, and linked run ID. Task deletion is not offered; cancellation preserves the log. Add an indexed nullable `task_id` to Runs for direct links and reporting.

The API accepts an RFC 3339 instant with an offset and stores UTC. The UI uses a local date/time picker and shows the selected IANA zone and resolved absolute instant before saving. For natural-language “in two hours,” the Tool also accepts an integer `delay_minutes`; the server resolves it using its own clock. Exactly one of `run_at` and `delay_minutes` is allowed. Reject nonexistent/ambiguous wall times unless the caller supplies an explicit offset. Bound scheduling to at least 1 minute and at most 1 year ahead; accept up to 20,000 prompt characters. `expires_at` is a per-Task deadline, defaulting to 60 minutes after `run_at_utc`, configurable from 1 minute to 24 hours after it. The UI calls this “Run if late by up to …”; it is a deadline for admission, not completion. A requested model is optional; omission resolves the target's concrete default at creation. UI and Tool offer the target runtime's current model catalog; reject a model from the wrong runtime. A “target's current default” choice is resolved to a concrete model at creation, so the schedule does not drift. Recheck that the target's runtime still matches at fire time; a mismatch blocks the Task instead of pairing a Claude model with Codex or vice versa. The normal configured backup model may still activate on an eligible provider failure; Task and Run views distinguish requested model from effective model and fallback reason.

The existing scheduler checks due Tasks after recurring Jobs. It atomically claims each due Task with a conditional Postgres update and a short lease; a second scheduler may recover only an expired claim. The claim fixes a deterministic run ID and increments a claim generation. The launch path must make Run insertion collision-safe (`INSERT ... ON CONFLICT DO NOTHING` or equivalent), then publish/sweep using the existing queued-Run machinery. `materialize_run` today does SELECT-then-INSERT and is **not** concurrently safe; do not call it unchanged from competing claims. Set and compare leases with the Postgres clock. In **one transaction**, lock the Task row, verify status `claiming`, current claim generation, owner, and unexpired lease; insert the Run with `ON CONFLICT DO NOTHING`; mark the Task launched and append its event; then commit before publishing. An expired claimant cannot insert after its successor blocked or expired the Task. A recovery first searches for the deterministic Run, then checks expiry/target state only if no Run exists. Repeated ticks, lease takeover, and Kafka redelivery must not create a second Run or logical request. The winning transition from `scheduled` to `claiming` is also the cancellation cutoff; a concurrent cancel gets a conflict if claim won. A task delayed by an outage is admitted for launch before its stored `expires_at`; after that it becomes `expired` with the last deferral reason and no Run. Temporary readiness, quota, run-gate, DB, and publish failures defer the Task with backoff and an event until the deadline; policy failures (disabled/deleted/quarantined target, revoked authority, incompatible runtime) block it permanently. Admission is the deadline, not Run completion: concurrency queues may delay the actual pod. Disabled, missing, quarantined, or runtime-incompatible targets become terminal `blocked` with a logged reason and a “Create replacement” action that opens a prefilled create form with time cleared. No automatic retries of a model failure: the linked Run and DLQ retain their normal recovery tools.

Task status describes scheduling (`scheduled`, `claiming`, `launched`, `blocked`, `expired`, `cancelled`); Run status describes execution (`queued`, `running`, `succeeded`, `failed`, DLQ, redriven, and so on). List, dashboard, and Tool output derive one human outcome—Upcoming, Starting, Running, Done, Failed, or Didn't run—from Task and Run state. Detail shows both raw states and reasons. A failed Run must never appear as a successful Task. A Run detail links back to its Task. An idempotent reconciler reads linked Run rows, updates `last_observed_run_state`, and appends a state event when it changes. It must handle lost Kafka notifications, restarts, and DLQ redrive of the **same Run**; the Task never launches a replacement Run. The Task log points to the Run's current result/error without copying its transcript.

## Identity, authority, and cost

Add a core `mcp__platform__tasks` Tool, placed on the narrow participant rung with Relay/Tickets, and a matching API route. Its actions are `schedule`, `list`, `get`, `reschedule`, and `cancel`; a read-only `models` action lists valid target models. It is default-granted to new and existing **persona and worker** agents, not code-owned system agents. The grant allows self-scheduling; cross-agent scheduling additionally requires an admin-managed `can_schedule` creator→target link (or an existing `can_invoke` grant). This is delayed invocation authority, so the Tool grant alone must never bypass an existing invocation boundary. The grant is described in the agent editor as **Schedule Tasks — may cause future runs of other agents with a selected model**. It does not confer general operator API access. The API checks the frozen per-run Tool grant, derives creator and root principal from the authenticated run token, and never trusts caller-supplied creator/run IDs. Agents may target user-defined persona or worker agents, including themselves; scheduling code-owned system agents requires admin. Each target has an admin-set `accept_scheduled_tasks` switch, default on for ordinary user agents and off for code-owned system and Workbench developer agents, checked at creation, fire, and dispatch. The `can_schedule` link is the creator-side authority; the target switch is a separate inbound veto. Configure links in the agent editor so personas can schedule workers and each other without granting general operator access. A creator whose agent is disabled/deleted or whose Tasks grant was revoked before fire has its pending Tasks blocked. The target runs under its own frozen definition and grants, not the creator's. Persist `requested_runtime` on the Run as well as the Task; at dispatcher definition freeze, compare it with the target's current runtime again and recheck creator enabled/granted, cross-agent link, target enabled/accepting, and other fire-time authority before pod launch. Block an incompatible or unauthorized queued Run before pod launch and log the reason on the Task. A runtime edit between Task fire and dispatch must never pair a model with the wrong harness. Scheduled prompt text is marked as a request from the named creator, never as a system instruction.

Non-admin model selection is limited to the target's current primary model, backup model, or explicit admin-managed `schedulable_models`; an admin may choose any valid model for the target runtime. The Tool can list/get Tasks it created or assigned to its own agent. An agent may reschedule/cancel only a Task it created while still pending; a human admin may manage all. The target agent can see its incoming Task and log but cannot rewrite the creator's request. Server-enforced limits: 20 creations per stable creator-agent identity per rolling day (cancellations still count), 50 pending per creator, and the existing maximum run-chain depth across immediate invocations, Relay mentions, and delayed Tasks. Enforce counters transactionally under concurrent creates, not as a read-then-write race. Persist the root run and inherited depth; a Task run has `parent_run_id=creator_run_id`, even if that run finished hours ago, and `depth=creator.depth+1`. Task-originated Relay replies must preserve that depth rather than reset hop to zero, or a Task → mention → Task chain bypasses the cap. Reject a Task whose inherited depth already reaches the cap at creation, with an actionable error; recurring work belongs in Jobs. The UI shows when a cap is reached. Firing still checks target enabled/readiness and existing quota/run gates; creating a Task does not reserve quota. Expose the selected runtime/model in the form so future cost is legible.

The Task has an optional `source_conversation_id`, `source_message_id`, and `delivery` choice. For an **internal** Relay source, default to “reply in source room” only if the target is a member and the creator could read it; preserve the originating thread through `trigger_message_id`. Recheck membership/visibility at fire and again before posting the result; if lost, use Task-log-only delivery and log the downgrade. Task-originated replies must carry the saved invocation depth in the Relay hop field. For an **external** Discord source, default to **Task log only** in v1 and require the creator's immediate acknowledgement to say explicitly that no automatic Discord reply will arrive. Surface the Task ID and a link when that provider supports links. This is a conscious v1 limitation, not a silent reminder failure. Provider-native result delivery is a separate phase with its own identity and thread-address validation. The existing `external_chat.queue_final` requires an addressed observation and cannot deliver a newly scheduled Task from just a conversation ID; never fake that path. A persona with its own connector may explicitly send a result during its Run under normal provider permissions. The Task log and Run link always work even when chat delivery does not.

## API and UI

`GET/POST /api/tasks`, `GET/PATCH /api/tasks/{id}`, `POST /api/tasks/{id}/cancel`, and paginated `GET /api/tasks/{id}/events`. `PATCH` changes title, prompt, model, time, zone, deadline, and delivery only while scheduled; require `version` for optimistic concurrency, log the editor, and attribute an edited prompt to that editor in the fired Run. Cancellation may also win while the linked Run is still queued: it atomically cancels that Run before dispatch, records an event, and suppresses a pod. A cancel that loses the claim/dispatch race returns a conflict with the Run link. `GET /api/tasks` supports status, target, creator, project, and due-window filters with pagination. Agent reads are filtered server-side. Creation supports an idempotency key scoped to the stable creator identity; retain a hash of the original request, return the original Task (including the originally resolved relative time) on matching retry, and conflict on a changed request. Creation/cancel/reschedule and per-creator caps must serialize against concurrent writes. Each mutation writes a TaskEvent in the same transaction and publishes `tasks.events` after commit for the UI feed; the database is the source of truth if Kafka is down. Extend `GET /api/runs` with a `trigger=task` filter for Reporting's drilldown.

Add **Tasks** to navigation beside Schedules. The list has Upcoming, Past, and Needs attention views, sortable by time, with creator/agent/model/outcome and direct links. Needs attention means blocked, expired, or launched with a failed Run. Empty views offer a create action; blocked/expired reason appears in the header, and a pending Task says “No run yet.” A detail drawer/page shows the full prompt, absolute and local times, origin, delivery, event log, and linked Run. The create flow selects agent first, then model from that runtime, then prompt and time; a clear preview says “Runs once at …” and “Run if late by up to …”. Explain ambiguous/nonexistent DST times with explicit offset choices, count prompt characters, show disabled/model-mismatch errors inline, and show an actionable reload on version conflict. The agent page gains a Tasks tab with “Assigned to this agent” and “Created by this agent”; the Dashboard shows the next few Tasks and recent blocked/failed ones. Keep recurring Schedules separate but cross-link “Need only once? Create Task.”

Extend Reporting with Task-triggered Run count, success/failure, model and token use, and a link to filtered Runs. Distinguish tasks that never launched (blocked/expired) from Runs that failed; do not divide by zero or call a queued Run successful. The Task detail is the primary operational log; existing Run transcript, metrics, quota and DLQ remain authoritative for execution. Help documents Tasks, Jobs, Tickets, the Tool grant, delivery, time zones, grace period, and limits.

## Implementation and verification plan

Ship in three gated slices, completing all three for the requested feature:

1. **Human-created one-time runs:** additive schema, claim/lease/recovery and collision-safe Run insertion, admin API and Tasks UI list/detail/create/edit/cancel. Keep recurring Jobs unchanged. Real Postgres tests use two scheduler instances, barriers between claim and insert, a crashed/stale claimant, concurrent cancel, and assert one Run row **and** one logical `run.requests` publish. Include deadline/backoff/readiness, UTC/DST, runtime drift at fire and dispatch, and a failed Run displayed as Failed. Build web before focused Playwright. Live-fire one human Task once, cancel another, and inspect links/events.
2. **Agent scheduling and authority:** scoped Tool and default self-scheduling grant, explicit cross-agent links, target opt-in, model allowlist, per-run identity, idempotency, transactional caps, lineage/hop propagation, and dispatch-time revocation fence. Use real per-run tokens and Postgres for the authorization/cap races. Verify a no-link cross-agent 403, an allowed persona→worker task, spoofed identity rejection, 30 concurrent creates at cap, idempotent retries, and a Task→mention→Task chain stopped at creation. Saturate concurrency, revoke creator grant or target opt-in, then release it: no pod may launch.
3. **Delivery, reporting, and Help:** internal Relay source-room reply with fire-time and post-time access checks; external source uses explicit log-only acknowledgement pending a separate provider-native design. Add dashboard/agent tabs, Schedules cross-link, Task-triggered Run count/success/failure/model/token use, blocked/expired counts, filtered Runs, and Help. Verify no duplicate Relay reply, no Discord impersonation, and durable Task/Run state after lost notifications and DLQ redrive of the **same Run ID**. Live-fire an agent-created cross-agent Task and inspect its Task log, Run, and report. Deploy code/schema before web; rollback code without dropping rows.

Across slices, run the concurrency tests on the production Python 3.12 line and a real Postgres instance. A Task that is 2 hours late under the 60-minute default expires; the same Task with a 4-hour deadline fires once. Temporary quota/readiness failure defers until recovery or deadline. A stale claimant resuming after takeover cannot create a Run. UI tests cover empty, blocked, expired, failed, version-conflict, DST, and cancel-race states.

## Open design checks for reviewers

- Is the broad default for `accept_scheduled_tasks` on Workbench developers appropriate, or should those few targets start disabled and be opted in by the admin?
- Is the 24-hour late-fire grace right for reminders and for potentially time-sensitive work?
- For external-origin reminders, is explicit persona connector delivery sufficient in v1, or should a provider-native Task result delivery path be a separate phase?
