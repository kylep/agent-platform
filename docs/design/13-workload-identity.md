# Design 13 — Workload identity: broker auth without bearer secrets

Status: DRAFT (talking through with Kyle)

Companion: `docs/security.md` (the model + status), design/12 (tools —
whose scoped tokens are the authz substrate this design authenticates).

## Problem

Broker auth today is a dispatcher-minted bearer key in the pod env:
role-scoped, per-run, revoked + orphan-swept — but still a replayable
secret owned by anything that executes in the pod. Kyle wants the full
five-layer ladder (2026-08-07): projected SA tokens, SPIFFE/SPIRE mTLS,
sender-constrained run tokens, user identity propagation (stubbed as a
single `admin` principal now, family-ready later), and central
authz+audit at the broker.

## Ordering vs design/12

Design/12 ships first on the current bearer scheme — its tools-only
*scoping* is orthogonal to *how the caller authenticates*, and Layer 5
needs 12's grant model to exist. 13 then swaps the authn substrate
under it, layer by layer, each independently shippable and reversible.

## Phase A — Projected SA tokens (Layer 1)

- Dispatcher provisioner creates a ServiceAccount `agent-<name>` per
  registered agent (GC'd with the agent, same heartbeat as other
  provisioning).
- Run Job pods get `serviceAccountName: agent-<name>` + a projected
  volume: bound SA token, `audience: ap-broker`, `expirationSeconds:
  600` (kubelet auto-rotates; reads always fresh).
- Runner sends it as the MCP Authorization header instead of
  AP_API_TOKEN.
- Broker validates via TokenReview (broker SA gains
  `system:auth-delegator`), caches JWKS/decisions briefly, maps
  `system:serviceaccount:<ns>:agent-<x>` → agent identity, then applies
  the run's grant scope (Phase C carries run context; until then the
  broker resolves the agent's *current* declared tools).
- Platform API trust: the broker becomes an authenticating frontend —
  it calls the API with its own service identity plus verified
  `X-AP-Agent` context over the existing netpol-restricted path. The
  API keeps accepting legacy per-run bearers during migration; flag-day
  removal once all agents ride SA tokens.
- **Fallback kept:** per-run keys remain the auth for `claude` CLI-less
  surfaces (nothing today) and break-glass.

## Phase B — SPIFFE/SPIRE mTLS (Layer 2)

- Deploy spire-server (+ sqlite datastore on the NUC) and spire-agent
  DaemonSet; k8s workload attestor. Registration entries generated by
  the dispatcher provisioner per agent SA (parent: node alias).
- SVIDs delivered via spiffe-csi driver volume; identity
  `spiffe://pai/agent/<name>`, TTL ~1h with rotation.
- Broker terminates mTLS itself (client cert required); peer SVID is
  the workload identity; the SA token from Phase A remains as a second
  factor during rollout, then becomes optional.
- Also mTLS the broker→executor and broker→API hops (SVIDs for
  services) — netpol stops being the only thing making those paths
  private.
- k3s note: this is the heavy phase (SPIRE operational complexity on a
  single NUC). It is deliberately last-but-one and the platform is
  fully functional without it; treat as the "learning-grade gold
  standard" it is.

## Phase C — Sender-constrained run tokens (Layer 3)

- Dispatcher issues a **run JWT** at Job creation: claims `run_id`,
  `agent`, `initiated_by` (Phase D), `tools` (the design/12 grant set),
  short exp (run TTL), and `cnf` binding — the pod's SVID SPIFFE ID
  (with Phase B) or, pre-SPIRE, the SA identity (aud+sub binding).
- Sent as a separate header (`X-AP-Run-Token`) alongside the workload
  credential. Broker requires: valid workload identity AND valid run
  JWT AND cnf/identity match. Scope evaluated from the JWT's frozen
  grant set (a mid-run manifest edit doesn't widen a live run).
- Signing: dispatcher keypair in a k8s Secret; broker holds the public
  key; rotation = dual-key acceptance window.

## Phase D — Principal model, admin-stubbed (Layer 4)

- `users` table (id, name, role, created_at) seeded with `admin`.
  `runs.initiated_by` FK, populated everywhere a run is born: UI/chat +
  Run Now + API → session user (admin today); cron/webhook/agent-invoked
  → the owning principal (admin) with the *chain* recorded
  (`initiated_via`: schedule/webhook/agent:<name>).
- The run JWT carries `initiated_by`; broker/API authorize on
  intersection(agent grants, user entitlements). Admin's entitlement =
  everything, so behavior is unchanged — but the check, the claim, and
  the audit field are real from day one.
- Family-later roadmap (documented, not built): user rows + per-user
  web sessions (login already exists; becomes per-user), per-user
  entitlements (which agents/apps/tools a user may drive), per-user
  rate/spend budgets, and UI attribution ("run started by …").

## Phase E — Central authz + audit (Layer 5)

- Authorization at the broker from declared grants (design/12 scoped
  tokens → Phase C frozen grant sets). Policy stays data (the manifest),
  not a DSL; OPA/Cedar only if rules outgrow "grant intersection".
- **Audit log:** append-only `tool_audit` table written by the broker
  for EVERY call: ts, run_id, agent, initiated_by, tool, args digest
  (sha256 of canonical args — not raw args, secrets hygiene), decision
  (allow/deny+reason), latency, result size. Surfaced: Reporting page
  panel + `/api/audit` (admin) + health-monitor watches denial spikes.
- Per-identity rate limits at the broker (token bucket per agent+tool);
  429s are audited and alerting-visible.

## Testing

- A: TokenReview path unit-tested with faked reviews; e2e: pod token
  rotates and calls keep working; legacy bearer still accepted until
  flag day (then a test asserts it 401s).
- C: cnf mismatch → 401; expired run JWT → 401; frozen-grant test (edit
  manifest mid-run, scope unchanged); replay from a second pod fails.
- D: every run-creation path sets initiated_by (test sweeps all
  entrypoints); chain recording for cron/webhook/invoked.
- E: audit row for allow AND deny; args digest stable; rate-limit 429
  audited; Reporting panel fixture.

## Rollout order

A (SA tokens, biggest win/cost ratio) → D (principal stub — small,
unblocks JWT claims) → C (run JWT + cnf-to-SA) → E (authz/audit — needs
C's frozen grants) → B (SPIRE last: strongest crypto, most ops weight,
upgrades C's cnf from SA-binding to SVID-binding when it lands).
